# 驗證報告：透明 WebView 下的原生地圖（方案 2）

- 日期：2026-11-17　裝置：ASUS I006D、Android 13（API 33）、Impeller
- 分支：`Aqutter/aqutter` 與 `Aqutter/aqutter-plugins` 的 `feature/2611171140-map-passthrough-spike`（不併入主幹）
- 範圍：只驗證 Android；iOS 沒有設備，未驗證

## 結論

**可行，且效能明顯好於鏡像。** 地圖直接畫在 Flutter 裡、放在透明 WebView 下面，網頁 HTML 疊在地圖之上，拖曳、縮放、點擊都能由網頁轉成語意手勢驅動地圖。建議做成正式功能，但有三個前置問題要先處理（見「限制與待處理」）。

| HTML 疊層在地圖之上 | 通過 | 返回鈕、座標條、五個按鈕疊在地圖上正常顯示與點擊 |

## 做法（本次實驗的實作）

- 殼：`AQUTTER_WEBVIEW_TRANSPARENT=true` 時 WebView 設為透明背景。
- plugin：`AQUTTER_MAP_PASSTHROUGH=true` 時 `buildUnderlay` 直接回傳 `GoogleMap`（不包 `AqutterNative`）；新增 `mode`、`gesture` handler；網頁端建立透明元素並把 pointer 事件換成 `pan`／`pinch`／`doubleTap`／`tap`，沿用既有 `AqutterMapGestureMapper`。
- 頁面：`html`、`body` 與地圖容器、外層背景層（例如 `bg-surface`）都要透明，這是在 nuxt-app 以暫時 CSS 做的（已還原）。

## Iteration 1：按需建立底層、圓角與遮罩（2026-11-17）

- **一開 App 就先看到地圖：已修。** 底層地圖改成網頁 `mount` 後才建立（`show` handler），`destroy` 後移除（`hide`）。實機確認啟動時是乾淨的深色畫面、首頁沒有地圖，進入地圖頁才出現。每次 `show` 換新的工作階段編號，連續 `hide`／`show`（切換版面）才會真的重建地圖；修之前會出現「地圖還停在舊位置、座標條已重置」。
- **手勢位置改以視窗大小正規化。** 原本以元素大小，元素不是滿版時換算會錯；改後在圓角卡片內拖曳，地圖移動量與手指一致（實機：拖 300 px，地圖上的標誌也移動約 300 px）。
- **圓角與遮罩實測（Android，nuxt-app 暫時頁面，不進版控）：**

| 版面 | 做法 | 結果 |
|---|---|---|
| 圓角卡片 | 容器 `border-radius: 36px`＋`box-shadow: 0 0 0 200vmax <surface>` 在四周蓋出不透明邊 | 通過，地圖被裁成圓角，卡片內拖曳、點擊正常 |
| 圓形 | 同上，`border-radius: 50%` | 通過 |
| 漸層遮罩 | 全屏不透明層＋`mask-image: radial-gradient(...)` 挖出柔邊的洞 | 通過，邊緣平滑淡出，手勢正常 |
| 半透明疊層 | 底部抽屜 `background: color-mix(... 55%, transparent)` | 通過，能看到地圖透出來 |
| 半透明疊層＋`backdrop-filter: blur` | 同上加 14px 模糊 | **無效果**：地圖不在網頁的圖層裡，模糊不到它（符合預期） |

- 這些效果是「在網頁畫不透明的邊、把洞留給底下的地圖」，地圖本身仍是滿版，只是被遮住；`clip-path` 沒另外測（`box-shadow` 與 `mask-image` 已驗證同類效果）。

## Iteration 2：位置同步與滾動（2026-11-17）

**做法的演變（三次嘗試，只有最後一種成立）：**

| 嘗試 | 結果 |
|---|---|
| `GoogleMap.padding` 讓相機中心落在洞中心 | 失敗。padding 不會移動既有畫面內容；連初始相機都在 padding 套上後才建立時，標記仍在螢幕中心，回報的相機座標也出現怪值 |
| 底層地圖維持螢幕大小，建好與每次 `moveTo` 後用 `scrollBy` 位移到洞中心＋整體平移跟著洞走 | 部分成立。洞在螢幕內時標記對得上；但洞一開始有一大半在螢幕外時，捲進來的部分是空白，因為地圖 view 只有螢幕那麼大 |
| **底層地圖與洞同大、同位置**（`Positioned` 依洞的矩形放置，洞移動只更新位置、洞大小改變才重建基準） | 成立。相機中心由構造直接落在洞中心，不需要補償；洞在螢幕外也沒關係 |

**實機結果（Android；暫時頁面）：**
- 圓角卡片：標記落在卡片中心。
- 滾動內容：卡片在內容中間，一開始完全在螢幕外（視窗高 392、卡片 top 640），用 DevTools 把頁面捲到 300／560／760，卡片進入畫面後地圖完整覆蓋整張卡片，邊緣與紅框貼合，標記始終在卡片中心。
- 傳遞延遲：`layout` 從網頁送出到 Dart 收到，五批各 60 筆，中位數 7～8 ms、p95 8～12 ms、最大 24 ms（含重新排版的批次）。
- 錯位：截圖（取樣間隔約 100 ms）看不出地圖與卡片邊緣有錯位；但看不到一兩幀（16～33 ms）等級的落後，這個沒有量到。
- 觸控衝突確認：手指從地圖洞內開始滑，是平移地圖、頁面不捲；從洞外的區塊開始滑才捲頁面（因為容器設了 `touch-action: none`）。
- 橫向也通過（視窗 872×392 css px）；測試時手機被轉成橫向，兩種方向的版面都沒出問題。

**這輪實測的限制：**
- 手勢位置與位移換算成「相對底層地圖」的版本，只有單元測試涵蓋；實機只確認點擊會回報經緯度，沒有用已知位置核對準確度，洞內平移比例也沒有重測（上一輪滿版時是 1:1）。
- 洞的大小改變（旋轉、縮放視窗）時以新矩形當基準，這條路徑沒有實機測。
- 地圖 view 與洞同大，洞很大（例如整頁高度的長卡片）時，記憶體與繪製成本比螢幕大小的地圖高，沒有量。
- `layout` 目前每個畫面最多一次；網頁的捲動由瀏覽器在另一條執行緒處理，不是每幀都保證有事件，快速甩動時的最大落後沒有量。

## 限制與待處理

1. **殼的初始透明設定在 Android 沒有生效。** 只設 `transparentBackground: true` 時畫面仍是白的；用 DevTools 強制底色透明就會透出底層。實驗中改成建立 WebView 後先設 `false` 再設 `true` 才生效（見殼的 `_onWebViewCreated`）。根因未查：核心的初始套用在 `AqutterWebView.kt:364`、執行期更新在 `:940`，兩條路徑看起來都對，但行為不同。正式版應在 aqutter_core 查清楚並修在核心，而不是在殼做兩段式設定。
2. **所有 plugin 的底層疊在一起。** 殼把每個 plugin 的 `buildUnderlay` 依序放進同一個 Stack，nuxt-app 另外裝的 mirror-demo 底層（不透明的格線動畫）會蓋在地圖上面。實驗時暫時關掉它。正式版需要決定多個底層的順序或只允許一個。
3. **頁面背景要由網頁配合。**（已用暫時 CSS 驗證可行；另外，要模糊底下的地圖做不到，只能半透明。） 網頁任何一層有不透明背景就看不到地圖，目前沒有機制保證，正式版至少要在 README 說明，最好由 plugin 提供一個明確的「進入／離開透明模式」呼叫，離開時恢復不透明（目前殼是啟動時一次性全域設定，所有頁面都透明）。
4. **手勢轉送是 JS 側換算。**（位置已改以視窗大小正規化。） 單指拖曳、雙指縮放、短按、雙擊都在網頁端判斷（短按 250 ms、位移 8 px、雙擊 300 ms），手感沒有與原生地圖逐項比對；慣性滑動（fling）與旋轉、傾斜沒有做。
5. **只在 texture 模式驗證。** Android 地圖維持原本的 texture 模式；Hybrid Composition 模式沒有測。
6. **未驗證：** iOS（沒有設備）、桌面平台（本來就用 JS 地圖）、鍵盤彈出、WebView 內捲動與地圖手勢衝突、電量與記憶體。

## 建議

- 做成正式功能，順序：先在 aqutter_core 查出透明初始設定不生效的原因（限制 1），再設計「透明模式」的啟用方式與底層順序（限制 2、3），最後補慣性滑動並實測 iOS。
- 驗證用的兩個 `dart-define` 鍵是實驗性質；轉正時要依 AGENTS.md 第 3 條三處成對（Dart 鍵、`aqutter-cli` 範本、`docs/environment.md`），或改成 plugin 設定而不是編譯期鍵。
